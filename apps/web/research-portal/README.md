# Research Portal

## Purpose and status

Company-managed web product for governed research workflows. React 19 + TypeScript + Vite SPA per [ADR-0001](../../../docs/decisions/ADR-0001-web-frontend-technology.md), styled with Tailwind CSS v4 and the shared [design system](../../../design-system/README.md) ([ADR-0002](../../../docs/decisions/ADR-0002-web-design-system.md)).

- **IMPLEMENTED (D1):** the portal shell, HC-090 ([#82](https://github.com/Medmas07/Hackcure_hackathon/issues/82)). Its sidebar groups the pages into projects and requests (dashboard, new project, protocol and documents, population, variables, participating hospitals, access request, request status), Compute-to-Data (workspace, executions, controlled results), and SciAgents. The home page lists the researcher's projects with their participating hospitals, access-request status, and Governance decision, states the Compute-to-Data boundary (code goes to the data; only controlled aggregate results come back), and shows notifications. It also shows loading, empty, and error states.
- **IMPLEMENTED (D1):** the researcher dashboard, HC-091 ([#83](https://github.com/Medmas07/Hackcure_hackathon/issues/83)), at `#dashboard`. It counts projects, requests under Governance review, still-valid authorizations, completed executions, and released controlled results. Each project shows its progress through the governed workflow (project, access request, Governance decision, Compute-to-Data execution, controlled result) and one next action linking to the relevant page; projects needing the researcher's attention come first. Governance approvals are listed with their conditions and validity, and one ending within 30 days or already expired raises a warning; an expired approval blocks the workflow until a new decision. Executions list the Hospital Nodes they ran on and their controlled result's disclosure check; the dashboard receives result release metadata only, never aggregate rows. The derivations are pure functions in `src/services/dashboard.ts`.
- **IMPLEMENTED (D1):** research project creation, HC-092 ([#84](https://github.com/Medmas07/Hackcure_hackathon/issues/84)), at `#new-project`. The researcher enters a title (10 to 150 characters, unique among their projects, ignoring case and spacing) and a scientific objective (30 to 1,000 characters). The project is created as a draft owned by the signed-in researcher and their organization, with no protocol, population, variables, hospitals, or access request; those are completed by HC-093 to HC-097, which the confirmation links to. A draft unlocks no Compute-to-Data page. The draft then appears on the home page and the dashboard. Identifiers continue after the fixture ones (`proj-003`), even in the empty scenario, so fixture executions are never attributed to a draft. Validation and creation are in `src/services/projectCreation.ts`.
- **IMPLEMENTED (D1):** research protocol and document upload, HC-093 ([#85](https://github.com/Medmas07/Hackcure_hackathon/issues/85)), at `#protocol`. The researcher picks one of their projects (the newest draft opens first) and deposits its research protocol (required before the access request) and, optionally, a data management plan and a patient information notice: PDF only, non-empty, 10 MB at most. A deposited document can be replaced or removed. Documents change only while the project is a draft without an access request; once submitted, they are shown locked, as the Governance / Ethics Authority reviews them. Fixture protocols are shown as received. Depositing a document requests no data access and unlocks no Compute-to-Data page. Validation, simulated upload, and the project update are in `src/services/projectDocuments.ts`.
- **IMPLEMENTED (D1):** research population definition, HC-094 ([#86](https://github.com/Medmas07/Hackcure_hackathon/issues/86)), at `#population`. The researcher picks one of their projects (the newest draft opens first) and describes the studied population in plain language (20 to 500 characters, the text the Governance review reads), with at least one structured eligibility criterion: an age range (whole years, 0 to 130) and/or a consultation period (at least one consultation between two dates, inclusive). These criteria mirror `DataScope.population` of the [HC-180 execution contract](../../../contracts/api/research/research-node-execution.v1.yaml), the only criteria a Hospital Node can apply so far; other conditions (diagnosis, treatment) go in the description and protocol. A preview lists the criteria each Hospital Node would apply. The population changes only while the project is a draft without an access request; once submitted, it is shown locked, and fixture projects show their description with their criteria marked unstructured. No patient is counted or selected: the population is a definition that participating Hospital Nodes would apply locally after authorization. Defining it requests no data access and unlocks no Compute-to-Data page. Validation and saving are in `src/services/projectPopulation.ts`; the draft-editing rule shared with HC-093 is in `src/services/projectCreation.ts`.
- **IMPLEMENTED (D1):** requested variables definition, HC-095 ([#87](https://github.com/Medmas07/Hackcure_hackathon/issues/87)), at `#variables`. The researcher picks one of their projects (the newest draft opens first), selects 1 to 10 variables from a MOCKED fictional catalog grouped by category (demographics, care pathway, conditions and treatments, measurements), and justifies why they are needed (20 to 500 characters, the text the Governance review reads). Each catalog variable carries the name a Hospital Node would receive in `DataScope.variables` of the [HC-180 execution contract](../../../contracts/api/research/research-node-execution.v1.yaml) (for example `age_band`, `hba1c`) and the French label fixture projects already use. The catalog offers only derived or coarsened variables: direct identifiers (name, birth date, address, record number) cannot be requested; quasi-identifiers (age band, sex, governorate) are flagged, and combining two or more warns that minimum-cell-size checks will mask more results. The variables change only while the project is a draft without an access request; once submitted, they are shown locked, and fixture projects show their variables matched to the catalog by label, with their justification marked unstructured. Requesting variables transmits no data and unlocks no Compute-to-Data page. The catalog, validation, and saving are in `src/services/projectVariables.ts`.
- **IMPLEMENTED (D1):** participating hospitals selection, HC-096 ([#88](https://github.com/Medmas07/Hackcure_hackathon/issues/88)), at `#hospitals`. The researcher picks one of their projects (the newest draft opens first) and selects at least one healthcare organization (hospital or private practice) from a MOCKED directory built from the fictional fixtures. Each shows its federation state: an organization approved by Governance with an online Hospital Node is eligible; one approved but whose node is degraded or whose DMI is disconnected can be selected with a warning that execution may fail there; one whose onboarding is not approved, or without a Hospital Node, is shown but cannot be selected. A preview lists the Hospital Nodes (`node_ref`) that would be asked to run the analysis after authorization. The selection is saved as organization references, as `target_organizations` of the [HC-182 job contract](../../../contracts/api/research/research-job-orchestration.v1.yaml) expects, and the home page and dashboard show it at once. It changes only while the project is a draft without an access request; once submitted, it is shown locked, as the Governance / Ethics Authority may authorize only part of it. Selecting a hospital contacts no Hospital Node, transmits no data, and unlocks no Compute-to-Data page. Eligibility, validation, and saving are in `src/services/projectHospitals.ts`.
- **IMPLEMENTED (D1):** research data-access request submission, HC-097 ([#89](https://github.com/Medmas07/Hackcure_hackathon/issues/89)), at `#submit-request`. The researcher picks one of their projects (the newest draft opens first). A checklist shows what the Governance review needs, the checks the Governance Portal's research review (HC-078) applies: a deposited protocol (HC-093), a population with at least one structured criterion (HC-094), variables with their justification (HC-095), and at least one participating organization with an approved Hospital Node (HC-096); each item links to the page that completes it. A summary shows what will be submitted. The researcher must acknowledge, as principal investigator, that the request authorizes nothing by itself, that the Authority may refuse it or authorize only part of it, that no raw data leaves the Hospital Nodes, and that the project can no longer be edited. Submitting creates a request under review without a decision (`rar-003` onward, even in the empty scenario), moves the project out of draft, and locks the protocol, population, variables, and hospitals pages; the dashboard then waits for the Governance decision. An incomplete project, a missing acknowledgement, or a project already submitted is refused. An already submitted project shows its request reference, submission date, status, and decision, with a link to request tracking (HC-098). Renewing an expired authorization with a new request is not supported at D1. Submitting unlocks no Compute-to-Data page. Readiness, validation, and submission are in `src/services/projectAccessRequest.ts`.
- **IMPLEMENTED (D1):** research request tracking, HC-098 ([#90](https://github.com/Medmas07/Hackcure_hackathon/issues/90)), at `#request-status`. Each of the researcher's access requests is shown with its reference, project, participating organizations, and status: under review, authorized, authorized but ending within 30 days, authorization expired, or refused; refused and expired requests come first, then those under review, then approvals, most recent first, with a count per status. A timeline shows the request's submission, its examination by the Governance / Ethics Authority, and the decision. A decision is shown with its reference, date, the fictional reviewer who recorded it, its rationale, conditions, and validity; an approved request links to the workspace, while a request under review, refused, or expired states that no execution is possible. A request submitted in this session (HC-097) is flagged as not transmitted: it stays under review and no decision can follow it. Projects without a request are listed with a link to the access-request page. Empty states cover a researcher without projects and without requests. The page only displays decisions: it cannot record, change, or anticipate one. The derivations are pure functions in `src/services/requestTracking.ts`.
- **IMPLEMENTED (D1):** Colab-like research workspace, HC-099 ([#91](https://github.com/Medmas07/Hackcure_hackathon/issues/91)), at `#workspace`. It opens only for a project whose Governance approval is still valid; otherwise it is shown locked, listing each project and why (request not submitted, under review, refused, or authorization expired). The researcher picks an authorized project and edits its notebook: markdown and Python code cells can be edited, added, and removed. The fixture notebook (`nb-001`) opens for `proj-001`; an authorized project without one starts from a starter notebook. A side panel shows the authorization context each run is bound to: the Governance decision and its validity, its conditions, the Hospital Nodes (`node_ref`) of the participating organizations, the population, the authorized variables (HC-180 `DataScope.variables` names), the output policy (aggregate table, the decision's minimum cell size, mandatory disclosure check), and the approved packages (`ctd`, the fictional preloaded Compute-to-Data API, `numpy`, `pandas`, `scipy`, `statsmodels`). A cell or the whole notebook can be run; each code cell is sent as a complete, independent analysis. Before anything is sent, deterministic checks read the cell's text: a still-valid authorization at run time, non-empty code, approved packages only, no file, network, or dynamic-code call (`open`, `exec`, `eval`…), no catalog variable outside the authorization, no `min_cell_size` below the decision's, and a warning when `ctd.release` is never called (nothing would come back). A cell failing a check is refused. Otherwise the run shows its execution state (queued, running, completed, refused, failed) and the stages of the fixture job: authorization check by the Governance Node, local execution in each Hospital Node, controlled aggregation, and disclosure check. An execution fails in a Hospital Node that is offline or whose DMI is disconnected; then no result, not even partial, is released. The output records the checks, the stages, and the SHA-256 of the code (`algorithm.sha256` of the HC-182 job contract), and is flagged when the cell has been edited since. The derivations, checks, and simulation are in `src/services/workspace.ts`.
- **IMPLEMENTED (D1):** Compute-to-Data execution visualization, HC-100 ([#92](https://github.com/Medmas07/Hackcure_hackathon/issues/92)), at `#execution`. It lists the researcher's executions, most recent first: the fixture job (`job-001`) and the latest run of each workspace cell sent in the session (`<cell>-run-<n>`); a cell refused by the workspace checks was never sent and is not listed. The selected execution shows its governed path in five phases: submitted, authorized by the Governance Node (with the decision it is bound to), run locally in each Hospital Node (one lane per `node_ref`, stating that the data stays in the node), aggregated, and completed after the disclosure check. Each phase is pending, running, completed, or failed; a failing Hospital Node stops the path there and no result, not even partial, is released. A detailed timeline lists every stage with its organization and time, and a provenance panel shows the decision, notebook and cell, submission and end times, and the SHA-256 of the code (unknown for the fixture job). The outcome links a released controlled result to the results page (HC-101), or states why none came back (no `ctd.release`, edited code not interpreted). "Rejouer" animates the recorded stages from submission, the Hospital Nodes running in parallel, and ends on the recorded state. The page is locked without a still-valid Governance approval, like the other Compute-to-Data pages, and shows empty states without projects or executions. The derivations and replay frames are pure functions in `src/services/executions.ts`.
- **IMPLEMENTED (D1):** research experiment result panel, HC-101 ([#93](https://github.com/Medmas07/Hackcure_hackathon/issues/93)), at `#results`. It shows the researcher's controlled results, most recently released first (the fixture `res-001` at D1), each with its project, its aggregate table (numbers in French notation, the first column as row header), and key figures: the minimum cell size, the Hospital Nodes combined, the number of aggregate rows, and when the disclosure check ran. A result whose disclosure check failed shows no value at all. A provenance panel shows the Governance decision, the source execution and notebook, the aggregation time, the SHA-256 of the code (unknown for the fixture job), and the fixture provenance note; it lists the Hospital Nodes (`node_ref`) whose local aggregates were combined and every release of the result: the fixture job and any workspace run of the unchanged fixture cell, labelled as returning the same fixture result without recomputing it. A notice states that the aggregate describes a population, not a patient: it is neither a diagnosis nor a recommendation and enters no medical record. Executions that released nothing are listed with their reason (in progress, failed in a Hospital Node, no `ctd.release`, or edited code not interpreted), linking to the executions page (HC-100). A link opens SciAgents (HC-102). The page is locked without a still-valid Governance approval, like the other Compute-to-Data pages, and shows empty states without projects or results. The derivations are pure functions in `src/services/results.ts`; the aggregate rows are read from the fixtures by `controlledResultTable` in `src/services/researchService.ts`, and only for a result whose disclosure check passed.
- **IMPLEMENTED (D1):** SciAgents research panel, HC-102 ([#94](https://github.com/Medmas07/Hackcure_hackathon/issues/94)), at `#sciagents`. It shows the SciAgents investigations of the researcher's projects (the fixture `inv-001` at D1), shaped like `Investigation` of the [HC-170 contract](../../../contracts/api/sciagents/scientific-investigation.v1.yaml). A boundary card states that SciAgents is an existing external system reached through that contract, that the adapter (HC-171) and the portal connection (HC-172) are PLANNED, and that only the question, opaque references, and summaries of controlled results that passed their disclosure check may be sent, never raw Hospital Node data. The investigation shows its question, project, and status; each hypothesis with the confidence SciAgents declares (low, moderate, high, or not reported; stated as not validating the hypothesis), the evidence supporting it, and the contradictions weakening it, each with numbered citations; and the citation list, where a controlled-result citation links to the results page (HC-101) and fictional publications are labelled. A notice states that the output is a research lead (`not_for_clinical_decisions`), neither a diagnosis nor a recommendation, and never becomes clinical data. The context panel lists the controlled results sent as context, flagging any that did not pass its disclosure check as not transmissible, and shows the HC-170 `InvestigationRequest` body the investigation corresponds to, without such results and marked as not sent. The provenance panel shows the provider, the demo adapter (no real adapter exists), the fixture origin, the absent SciAgents reference, and the fixture note. A result whose references do not all resolve within it is withheld entirely; a failed investigation shows its error and that no hypothesis was produced; a queued or running one says so. The page is not a Compute-to-Data page and stays available once an authorization expires; it shows empty states without projects or investigations. Asking a new question is not possible at D1 (HC-172). The derivations are pure functions in `src/services/sciagents.ts`; the fixture is mapped to the contract shape in `src/services/researchService.ts`.

## Commands

From inside `apps/web/research-portal/` (run `npm install` in [`design-system/`](../../../design-system/README.md) once as well):

| Purpose | Command |
|---|---|
| Install dependencies | `npm install` |
| Dev server on <http://localhost:5175> | `npm run dev` |
| Type-check and production build | `npm run build` |
| Lint | `npm run lint` |
| Unit tests | `npm test` |
| Preview the build | `npm run preview` |

Demo scenarios: append `?demo=vide` (no research project), `?demo=erreur` (simulated service failure), `?demo=echec-depot` (the first document upload is interrupted), `?demo=echec-execution` (the first workspace run fails in a Hospital Node), or `?demo=echec-sciagents` (SciAgents did not answer the investigations in time) to the URL. Pages are addressed by hash, for example `#request-status` or `#workspace`.

## Responsibilities and owned concepts

- Researcher onboarding/subscription display, projects, protocols, requested cohorts/variables, and request status.
- Colab-like interface, Compute-to-Data job visualization, controlled results, and SciAgents access.

## Communication boundaries

The portal will use Research Service, Governance, job, and SciAgents Integration contracts. It never connects directly to hospital databases.

## Non-responsibilities

It does not grant ethics approval, export unrestricted raw clinical data, execute inside hospitals itself, or implement SciAgents.

## Expected contracts

PLANNED project/request, governance-status, research-job, controlled-result, and SciAgents request/response contracts.
