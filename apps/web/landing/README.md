# Landing (MedOS) and Hospital Portal

## Purpose and status

Company-managed web product: the **MedOS** public landing page and the hospital onboarding portal. Formerly `apps/web/hospital-portal/` (package `hospital-portal`); renamed `landing` when the landing page was added; why the old dashboard-first portal was a misconception is recorded in [ADR-0013](../../../docs/decisions/ADR-0013-medos-landing-and-hospital-journey.md). React 19 + TypeScript + Vite SPA per [ADR-0001](../../../docs/decisions/ADR-0001-web-frontend-technology.md), styled with Tailwind CSS v4 and the shared [design system](../../../design-system/README.md) ([ADR-0002](../../../docs/decisions/ADR-0002-web-design-system.md)).

Hash routes (`src/route.ts`):

| Hash | Page |
|---|---|
| none, or an in-page anchor (`#fonctionnement`, `#ecosysteme`, `#confiance`, `#etablissements`) | MedOS landing page |
| `#adhesion/<step>` | Guided journey started by "Télécharger l'instance pour hôpitaux" |
| `#connexion` | Simple sign-in page: **authentication not implemented**, nothing is checked, stored, or sent, and submitting does nothing for now |

- **IMPLEMENTED, static content:** MedOS landing page (`src/landing/`), adapted from the Medora design concept to the design-system tokens (light and dark themes) and to the product vision. A scroll-driven Three.js scene (`three`, `@react-three/fiber`, GSAP ScrollTrigger, Lenis) shows scattered records gathering into one Hospital Node, then threads to the Governance node, two hospitals, the patient and clinician apps, and research; the Governance node lights up. Three.js is lazy-loaded only on screens at least 768 px wide with WebGL; phones and browsers without WebGL get a CSS fallback, and `prefers-reduced-motion` fixes the camera and disables smooth scrolling. The copy describes the product vision; it claims no security, clinical validation, or production readiness, and the footer labels the page as a demo with fictional data.
- **IMPLEMENTED (reuses the onboarding pages), MOCKED services:** guided journey at `#adhesion/<step>` (`src/JourneyApp.tsx`). The landing button "Télécharger l'instance pour hôpitaux" opens the onboarding forms one after the other (registration, profile, documents, agreements, technical and DMI questionnaires), then the automated checks and submission, the human review and the Governance decision, then the **Node configuration guide before the download page** and its download button, then the installation guide and the Node status page. Each step renders the same page as the portal (`src/views/StepView.tsx`), with a progress sidebar and previous/next buttons. The journey starts from an empty dossier (`empty` scenario) unless a `?demo=` scenario is in the URL. **The journey never approves anything**: the configuration and download stay locked until a Governance decision exists. While a submitted dossier awaits a decision, a labelled link reloads the journey on the `?demo=decision-approuvee` scenario, which shows the fictional Cap Azur dossier with a simulated approval; the visitor's local entries are not kept.

- **Removed on 2026-10-11:** the dashboard-first "Espace établissement" (sidebar `AppShell`, onboarding dashboard at `#overview`, `src/PortalApp.tsx`, `src/views/OverviewView.tsx`). Its entry points are replaced by a "Se connecter" button leading to `#connexion`; old portal hashes now show the landing page. The onboarding and Node pages described below are reached through the journey. `src/views/ClinicianAlertsView.tsx` (HC-203) has no entry point any more; it is kept until its owner decides where it belongs. The per-ticket notes below still mention the sidebar and dashboard, which no longer exist.
- **IMPLEMENTED (D1):** the portal shell, HC-050 ([#57](https://github.com/Medmas07/Hackcure_hackathon/issues/57)). It has a sidebar with the onboarding workflow (registration, profile, documents, agreements, technical and DMI/HIS questionnaires, automated review, human review, Governance decision) and the Hospital Node pages (configuration, download, installation guide, status). The onboarding dashboard shows the application status, progress, next step, step timeline, and notifications. It also shows loading, empty, and error states.
- **IMPLEMENTED (D1), MOCKED submission:** hospital registration flow, HC-051 ([#58](https://github.com/Medmas07/Hackcure_hackathon/issues/58)), at `#registration`. A three-step form (establishment, responsible manager, review and send) with per-step validation and two required confirmations, one of them stating that registration is not approval. `src/services/registrationService.ts` simulates submission with a delay. It re-validates the form, rejects an establishment name already in the fictional registry, and returns a deterministic reference (`REG-<date>-<short name>`). The result is kept in memory only, as a local `draft` application that updates the dashboard; reloading the page discards it. No account is created and nothing leaves the browser. A "fill with the fictional example" button enters the canonical Cap Azur data. When an application already exists (the default fixture), the page shows its registration summary.
- **IMPLEMENTED (D1), MOCKED save:** organization profile, HC-052 ([#59](https://github.com/Medmas07/Hackcure_hackathon/issues/59)), at `#profile`. It holds the administrative information sent with the application: legal identity, address and contact, legal representative, data protection officer, and an optional security contact. Without a registration, the page shows an empty state linking to registration. For a local `draft` application, the form is prefilled from the registration and can be saved and edited again. `src/services/profileService.ts` validates the profile (required fields, formats; the security contact must be complete if given) and simulates the save; the result is kept in memory only. Once the application is submitted for review (the default fixture), the profile is read-only. The canonical Cap Azur profile lives in `demo-data/governance.json`; its missing security contact is shown as a non-blocking recommendation.
- **IMPLEMENTED (D1), MOCKED upload:** administrative documents, HC-053 ([#60](https://github.com/Medmas07/Hackcure_hackathon/issues/60)), at `#documents`. A checklist of the three required documents (articles of association, operating licence, insurance certificate) with their status. `src/services/documentService.ts` validates each file (PDF, JPEG, or PNG, matching extension, not empty, at most 10 MB) and simulates the transfer with visible progress. **The file content is never read or sent**: only its name, size, and media type are kept, in memory. A local `draft` application can deposit, replace, and remove every document. An application under review (the default fixture, whose insurance certificate is missing) can still provide missing or rejected pieces, but not replace received ones. A decided application is read-only.
- **IMPLEMENTED (D1), MOCKED acceptance:** agreements workflow, HC-054 ([#61](https://github.com/Medmas07/Hackcure_hackathon/issues/61)), at `#agreements`. The two required agreements (data processing agreement, federated governance charter) are shown with their version and key clauses. **The agreement texts are fictional summaries with no legal value**; their clauses restate the ecosystem's invariants (data under hospital control, no central DMI access, explicit authorization, compute-to-data, Governance decides, AI advisory). Accepting requires an explicit read-and-accept confirmation; `src/services/agreementService.ts` simulates the acceptance and records the accepted version, date, and signatory, in memory only. A local `draft` application can accept and withdraw; once submitted (the default fixture, with both agreements accepted), acceptances are read-only records.
- **IMPLEMENTED (D1), MOCKED save:** technical onboarding questionnaire, HC-055 ([#62](https://github.com/Medmas07/Hackcure_hackathon/issues/62)), at `#technical`. It collects the planned deployment environment of the Hospital Node: hosting type, operating system, CPU, memory, storage, bandwidth, a network description, and yes/no answers on DMZ, outbound HTTPS, container execution, and backups; the technical contact is the registered manager. `src/services/technicalService.ts` validates the answers (all required, explicit yes or no, bounded whole numbers) and simulates the save, in memory only. **No hardware threshold or readiness verdict is applied**, because no requirement defines one. The DMI / HIS answers belong to HC-056 and are kept when deployment answers change. A local `draft` application can fill in and edit the questionnaire; once submitted (the default fixture), it is read-only.
- **IMPLEMENTED (D1), MOCKED save:** DMI / HIS information questionnaire, HC-056 ([#63](https://github.com/Medmas07/Hackcure_hackathon/issues/63)), at `#dmi`. It describes the existing DMI / HIS (product and version, database, hosting), the integration methods it offers (HL7 v2, FHIR API, file export, read-only database replica, or none, which is exclusive), whether a test environment exists, and optional known constraints. **These answers only prepare the DMI Adapter local to the Hospital Node**: nothing connects to a DMI, no central service ever does, and the page asks users not to enter credentials, passwords, internal addresses, or patient data; the form has no field for them, and a test pins the exact list of fields. The answers complete the technical questionnaire, which is required first; `src/services/dmiService.ts` validates and simulates the save, in memory only, and the technical page keeps every DMI answer when it saves again. A local `draft` application can fill in and edit; once submitted (the default fixture), it is read-only.
- **IMPLEMENTED (D1), MOCKED checks and submission:** automated onboarding review, HC-057 ([#64](https://github.com/Medmas07/Hackcure_hackathon/issues/64)), at `#automated-review`, in the order the product vision gives: (1) a **deterministic completeness check** that blocks submission while any earlier step is incomplete (profile, the three documents, both agreements, technical and DMI questionnaires), each finding linking to its page; (2) an **assisted review that is SIMULATED**: fixed rules stand in for an LLM to flag inconsistencies (profile name or city differing from the registration, no security contact, no known DMI integration method, no DMI test environment, outbound HTTPS refused); **no model is called**, every result is labelled "IA simulée · indicatif" with its provenance, and its remarks never block (AI Services now serves a real LLM-assisted review, [HC-154](../../../services/ai/README.md#hospital-document-review-hc-154), which this portal does not call yet); (3) human review by the Governance / Ethics Authority. `src/services/reviewService.ts` runs the checks and, after an explicit confirmation, simulates the submission: the checks run again, the results are recorded (the assisted step marked `mocked` and `advisory`), and the application moves to `human_review` with a pending human-review step. **Submission approves nothing**; it locks every earlier page. For an application already under review (the default fixture), the page shows the recorded results.
- **IMPLEMENTED (D1), MOCKED refresh:** human validation state, HC-058 ([#65](https://github.com/Medmas07/Hackcure_hackathon/issues/65)), at `#human-review`. **A status page only**: human review belongs to the Governance / Ethics Authority, and the portal offers no way to act on, speed up, or decide it. It shows a timeline (submitted, automated checks, human review in progress, decision to come), whether a reviewer is assigned **without naming the reviewer**, the documents still expected (with a link to Documents), supplements deposited after submission, and the application's notifications. No decision deadline is shown, because none is defined. `src/services/humanReviewService.ts` derives these states (not submitted, not recorded, pending, completed) and simulates a status refresh that never invents a decision. Before submission, the page points to the automated review; once the review is completed, it points to the decision page (HC-059).
- **IMPLEMENTED (D1), display only:** hospital approval page, HC-059 ([#66](https://github.com/Medmas07/Hackcure_hackathon/issues/66)), at `#decision`. It shows the decision of the Governance / Ethics Authority on the application, attributed to the Authority rather than a named reviewer: outcome, date, reference, validity, rationale, and any conditions. **The portal never makes, changes, or contests a decision** and invents no appeal process. Without a submitted application it shows an empty state; while the review is open, "Décision en attente". The canonical Cap Azur application has **no decision**, because the demo approves it live in the Governance Portal; the scenarios `?demo=decision-approuvee` and `?demo=decision-refusee` show a **simulated** decision as the hospital would receive it, clearly labelled. An approval unlocks the Hospital Node pages and still lets missing documents be provided, since its conditions can require them; a rejection keeps every step locked and is shown as "Rejetée" rather than as an action to take.
- **IMPLEMENTED (D1), MOCKED generation:** Hospital Node configuration summary, HC-060 ([#67](https://github.com/Medmas07/Hackcure_hackathon/issues/67)), at `#node-configuration`, available only after an **approval** (use `?demo=decision-approuvee`). `src/services/nodeConfigService.ts` derives, in the browser, the Node identity (`node-hospital-c`, validated against the Federation `OpaqueRef` pattern), the organization, the approval decision reference that the Federation node registry needs, the local port reserved by ADR-0003 (8103), local storage, the declared environment, and the DMI Adapter inputs (to configure locally; the adapter is PLANNED). It previews the configuration file with **exactly the fields the Hospital Node loads and validates** (`instances/hospital-node/infrastructure/config.py`); a test reads that file and fails if the two drift. **The configuration holds no secret.** It states one limitation openly: the current Node requires a fictional clinical records file, which does not exist for Hospital C, so it would refuse to start with this file. Before approval, after a rejection, or without an application, nothing is generated.
- **IMPLEMENTED (D1), MOCKED package:** Hospital Node download page, HC-061 ([#68](https://github.com/Medmas07/Hackcure_hackathon/issues/68)), at `#node-download`, available only after an approval. `src/services/nodePackageService.ts` assembles, in the browser, a **demo package: a single JSON manifest** holding the exact HC-060 configuration file, the node, organization, and approval references, the declared environment, the inputs for the local DMI Adapter, and the known limitations. It states what the product vision's package would add and why it is absent: container images (OPEN, no container decision), node identity and secrets (PLANNED, generated locally at installation and never sent by the portal), and an installation helper (PLANNED). **It contains no executable and no secret, and the portal installs nothing.** Preparation is simulated step by step; the file is saved through the browser with its SHA-256 checksum (Web Crypto) shown for verification, and the download is recorded in memory so the step completes. Before approval or after a rejection, no package is offered.
- **IMPLEMENTED (D1), declarative:** Hospital Node installation guide, HC-062 ([#69](https://github.com/Medmas07/Hackcure_hackathon/issues/69)), at `#node-installation`, available after an approval. `src/services/installationService.ts` follows the product vision's installation flow in nine steps, each labelled honestly: administrator approval (required: nothing is installed without it), host environment, package checksum (`sha256sum` against the checksum recorded at download), container runtime (**not decided**), configuration extraction into the file the Hospital Node loads, local secrets (**planned**: generated on site, never by the portal), launch, `GET /health`, and registration with the Federation node registry (`PUT /v1/registry/nodes/{node_ref}`, unauthenticated in the demo and without Governance verification). Commands use the real values (node reference, port 8103, checksum, approval reference) and can be copied. The hospital can mark each step done; **this is a declaration, not a verification**, so the installation step reads "déclarée terminée (non vérifiée)". The portal installs nothing and contacts no infrastructure.
- **IMPLEMENTED (D1), MOCKED status:** Hospital Node status dashboard, HC-063 ([#70](https://github.com/Medmas07/Hackcure_hackathon/issues/70)), at `#node-status`. `src/services/nodeStatusService.ts` derives five indicators from the Node summary the portal holds: connectivity (online, degraded, offline), DMI Adapter (connected, disconnected), version (compared with `NODE_VERSION` of the Hospital Node runtime, kept in sync by a test), health checks (liveness, local storage, DMI Adapter, Federation registry), and synchronization (up to date, interrupted while the DMI Adapter is disconnected, unknown while offline, with the last synchronization time). No time threshold is applied, because none is defined. **The portal never contacts the Node, its DMI, or the Federation Service**, and no health-status contract exists yet; the refresh is simulated and returns the known state. The canonical Cap Azur data has no installed Node, so after approval the page says no state was received, even when every installation step is declared done. The scenarios `?demo=noeud-en-ligne`, `?demo=noeud-degrade`, and `?demo=noeud-hors-ligne` simulate an approved application with an installed Node reporting that state, labelled as simulated. Node pages are shown as locked until a Governance approval exists.
- **MOCKED:** `src/services/onboardingService.ts` reads the canonical fictional fixtures ([`demo-data/`](../../../demo-data/README.md), [ADR-0005](../../../docs/decisions/ADR-0005-canonical-demo-data.md)) in the browser with a simulated 400 ms delay. The signed-in identity is the fictional manager of Centre Hospitalier Cap Azur (`usr-mehdi`, application `app-hospital-c`); there is no authentication. Step states are derived from that application. No onboarding API or contract exists yet. Every page carries a `DemoBanner`.

## Responsibilities and owned concepts

- Registration submissions, administrative documents, agreements, and technical questionnaires.
- Display of completeness, assisted-review, human-review, and approval states.
- Display of generated Hospital Node configuration, package guidance, and operational status.

## Communication boundaries

The portal will use explicit APIs/contracts to onboarding services and display Governance Node decisions. It must not access governance or hospital databases directly.

## Non-responsibilities

It does not approve hospitals, own clinical data, connect to hospital DMI/HIS systems, or install privileged software silently.

## Expected contracts

PLANNED onboarding submission, document metadata, technical questionnaire, approval-status, Node-configuration, package, and health-status contracts.
