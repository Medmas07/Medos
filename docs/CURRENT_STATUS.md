- **AI Services runtime skeleton — VALIDATED (local):** [`services/ai/`](../services/ai/README.md) is a FastAPI service with `GET /health`, framework-free Domain/Application layers, and pytest tests (use case, HTTP, layer boundaries). Its tests, ruff checks, and local `fastapi dev`/`fastapi run` servers were verified. It is not deployed.
- **Hospital Node runtime skeleton — IMPLEMENTED:** [`instances/hospital-node/`](../instances/hospital-node/README.md) is a FastAPI app with pinned dependencies and pytest tests (use case, HTTP, layer boundaries). One codebase runs one process per hospital: each instance loads its hospital identity (node and organization ids), port, and local storage location from the JSON file named by `HOSPITAL_NODE_CONFIG`, and refuses to start without a valid one (HC-112, D2). Fictional demo configurations exist for Hospital A, Hospital B, and the private practice. `GET /health` (HC-111, D2) is a liveness check reporting the configured identity, its `patient_history`, `audit_events`, and `access_grants` capabilities, the clinical repository's record counts, and a notice of what is MOCKED. It serves the patient history API (HC-114, D2), its side of [`hospital-node-federation.v1.yaml`](../contracts/federation/hospital-node-federation.v1.yaml): `GET /v1/federation/node` and `POST /v1/federation/queries`. A query is parsed strictly (`400`), its authorization is checked before any record is read and denied by default (`403`, same answer whether or not the patient is known), and only entries inside the requested scope are returned, each naming its source node. The authorization check is MOCKED (see Mocked behavior). Every query the node answers or refuses is recorded in its own audit trail (HC-116, D2), served by `GET /v1/audit/events` per [`hospital-audit-events.v1.yaml`](../contracts/api/hospital-audit/hospital-audit-events.v1.yaml) with filters by patient, query, and outcome: events name the requester, purpose, scope, authorization, and disclosed record references, never clinical content, and nothing is disclosed if the event cannot be recorded. The trail is kept in memory only (lost on restart) and its readers are not authenticated. It serves the access grants API (HC-115, D2) per [`patient-access-grants.v1.yaml`](../contracts/api/patient-access/patient-access-grants.v1.yaml): list a patient's grants with their status (`active`, `expired`, `revoked`), record one, and revoke one; the node enforces them in its patient history API at once. The grant store is MOCKED (in memory, seeded from the fictional `access.json`, lost on restart, never shared with other nodes), and its callers are not authenticated. Tests, ruff, and Hospital A and B running side by side on ports 8101 and 8102 were checked; the three demo nodes running with the Federation Service in `http` mode returned Patient A's `complete` timeline over real HTTP, every node answered `denied` for another purpose, and discovery reported each node `discovered`; each node's audit trail then listed its own `disclosed` and `denied` events with the Federation Service's `query_id`. Nothing uses its storage location yet, and it is not deployed.
- **AI provider port — IMPLEMENTED:** the provider-neutral `AiProvider` port (HC-151) lives in `services/ai/application/`. Adapters: Claude through the Claude Agent SDK, local Ollama, and a deterministic mock, combined by `FallbackAiProvider` ([ADR-0006](decisions/ADR-0006-ai-provider-strategy.md)). Outputs carry provenance and stay pending human review.
- **Real clinical extraction — IMPLEMENTED (D3), live-checked locally, not clinically validated:** in model mode (the default), `POST /v1/clinical-extractions` calls Claude first and the local Ollama model as fallback (HC-153). Items whose evidence quote is not in the source text are dropped; drafts stay pending clinician review; if no provider answers, the API returns `503 extraction_unavailable`. Automated tests use test doubles; opt-in live tests and local end-to-end calls against the real providers passed on the fictional demo transcript. Extraction quality has not been measured with an evaluation set.
- **Governance Portal shell, dashboard, pending hospital approval list, hospital approval review, synchronization request list, synchronization decisions, research access request list, research access review, governance audit timeline & blockchain proof explorer (HC-070, HC-071, HC-072, HC-073, HC-074, HC-076, HC-077, HC-078, HC-079, HC-080) — IMPLEMENTED (D1):** [`apps/web/governance-portal/`](../apps/web/governance-portal/README.md) is a React 19 + TypeScript + Vite SPA configured per [ADR-0001](decisions/ADR-0001-web-frontend-technology.md) and [ADR-0002](decisions/ADR-0002-web-design-system.md). It consumes `@hackcure/design-system` and canonical fictional demo fixtures (`demo-data/governance.json`, `organizations.json`, `people.json`, `notifications.json`). It implements a complete governance dashboard with reviewer alerts (Pr Olfa Hamdi), federated hospital nodes health monitoring, executive KPI metrics, prioritized action queues, decision records, cryptographic SHA-256 ledger proof verification, and resilient loading/empty/error states. The pending hospital approval list (HC-072) opens on the applications awaiting review, with queue counts (missing documents, advisory AI findings), search by name, city, DMI, or reference, document-completeness indicators, and an empty state; an application decided in the session leaves the queue. The hospital approval review (HC-073) lets the governance reviewer approve or reject an application awaiting review: the form lists missing documents, unaccepted agreements, the deterministic completeness findings, and the advisory AI findings; it requires an explicit acknowledgement of those findings, a rationale, and a condition to approve an incomplete application, and refuses a reviewer who is not a governance reviewer or belongs to the applicant organization. The recorded decision is SIMULATED (see Mocked behavior). The synchronization request list (HC-074) shows each request's organizations, pseudonymous patient id, purpose, scope, duration, consent basis, and status as of today, so an approved request whose decision has lapsed shows as expired; it orders pending requests first, filters by status, and shows an empty state. A pending synchronization request can be approved or refused (HC-076) after deterministic checks of the organizations' approval, the consent basis (the patient grant's status, expiry, patient, and scope), and the duration: approval is impossible while a check fails, and an approval never outlasts the patient grant it relies on. Only a governance reviewer outside both organizations may decide; the recorded decision is SIMULATED. The research access request list (HC-077) shows each request's project, investigator, participating organizations, and status as of today (under review, authorized, expired, rejected), orders requests under review first, and filters by status with an empty state. A research access request under review can be approved or rejected (HC-078) after checks of its project, protocol, population and variables, and participating organizations; an approval only narrows the request and records the authorized organizations, variables, validity (at most 12 months), and minimum output cell size (at least 10, D1 demo policy), as the research execution contract expects. The recorded decision is SIMULATED. The governance audit timeline (HC-079) lists the Governance Node's minimized audit events newest first, in plain language with each decision's subject and outcome, actor, organizations, and ledger-proof status, filtered by domain and organization; decisions recorded in the session appear at once, labelled simulated. It reads fixtures and local state, not a Governance Node audit API (HC-134 is PLANNED). The blockchain proof explorer (HC-080) lists each simulated ledger proof with its event type, hash, timestamp, organizations, and a verification state recomputed in the browser (hash, link to its audit event, minimized payload), clearly marked MOCKED BLOCKCHAIN; canonical hashing now matches `check_fixtures.py` at every depth. Production build, lint, and Vitest suite pass; the review flow was driven in headless Chrome (validation errors, confirmation, recorded decision, cleared pending badge, audit event, reset) with no console error. Fixed dev port is 5174.

- **DMI Adapter — PLANNED:** its Hospital Node-local boundary exists, but no port, mapping, configuration, fixture, or implementation.
- **Federation Service — partially IMPLEMENTED:** the runtime serves the federated patient query. By default it asks each registered Hospital Node over real HTTP (HC-145), parses answers strictly, and marks a result `mocked` when a node says it answered from fixtures. The Hospital Node runtime serves the endpoint (HC-114) from MOCKED records, so live answers are marked `mocked`; a node that is not running is reported `unavailable`. `FEDERATION_NODES=simulated` switches to the HC-141 MOCKED nodes (see Mocked behavior). In `http` mode, failures are handled (HC-147): connection errors, `503`, and timeouts are retried once with the same `query_id` within a 5-second budget, and a node that failed 3 consecutive queries is paused for 30 seconds and reported `not_asked` with `circuit_open` (in memory). Also in `http` mode, a node whose latest capability check shows it cannot answer is not asked and is reported `not_asked` with the reason (HC-146); nodes never checked or unreachable are still asked. The service also serves a node registry (HC-142): register, update, list, get, and remove nodes. Federated queries ask only registered nodes. The registry is kept in memory, its write operations are unauthenticated, and the Governance approval reference on each registration is not verified. Capability discovery (HC-143) calls each registered node's `GET /v1/federation/node` over real HTTP on request and keeps the latest result in memory. A running Hospital Node is reported `discovered`; one not running is `unreachable`. Temporary sync authorization (HC-144): before any node is asked under a synchronization decision, the service checks it with the Governance Node over real HTTP and asks only the organizations Governance authorizes. No Governance Node exists yet, so live sync-basis queries return `503` and ask no node; the authorized path is covered by tests only. Persistent registry storage, node identity and service authentication, Governance verification of patient access grants (by the service and by each node), synchronization, and audit are PLANNED.

## Mocked behavior

- **Canonical demo data — MOCKED (D1):** `demo-data/` holds fictional JSON for three hospitals, a private practice, the Governance / Ethics Authority, three patients, clinicians, encounters, medications, labs, access grants, synchronization and research requests, decisions, audit events, simulated ledger proofs, research jobs, a SciAgents fixture, alerts, and notifications ([ADR-0005](decisions/ADR-0005-canonical-demo-data.md)). `python demo-data/check_fixtures.py` passes. Medicines and the interaction rule are invented and not validated. The Federation Service's simulated nodes read it (HC-141).
- **AI clinical extraction fixture mode — MOCKED (D1):** with `AI_EXTRACTION_MODE=fixture`, `POST /v1/clinical-extractions` in [`services/ai/`](../services/ai/README.md) uses the HC-152 deterministic fixture extractor instead of a model. It recognises one fictional demo transcript (Patient A) and returns a fixed draft; any other text returns an empty draft. Every response is labelled `provenance.mocked: true` and `review_status: pending_clinician_review`. Its responses are checked against the contract by automated tests. This is not clinical intelligence.
- **AI provider mock — MOCKED (D1):** `DeterministicMockAiProvider` (HC-151), used in fixture mode, returns fixed `[MOCK]` templates and never echoes input. It is not AI and not validated intelligence.
- **Hospital Node clinical repository — MOCKED (D2):** each [`instances/hospital-node/`](../instances/hospital-node/README.md) instance loads, at startup and read-only into memory, the fictional `demo-data/records/` file named by its configuration (HC-113). It refuses to start if the file is not marked fictional, is held by another organization, or holds a malformed record. A `ClinicalRepository` port returns one patient's records held by that node; only the patient history API discloses them, after its authorization check (HC-114). Tests and Hospital A and B running side by side were checked, as was a refused start with another hospital's file. This is not real storage, a DMI integration, or a FHIR model; persistence and FHIR mapping are OPEN.
- **Hospital Node authorization check — MOCKED (D2):** the patient history API (HC-114) checks each query's basis with a fixture verifier that reads the fictional Governance decisions and synchronization requests in `demo-data/` at startup, read-only, and looks grants up in the node's MOCKED access grant store, and refuses to start on a file not marked fictional. It applies the HC-141 simulated nodes' rules, denies by default, and accepts a synchronization decision only at the node it targets. It stands in for node-side verification with the Governance Node, which is OPEN. This is not real authorization or production security.
- **Hospital Node access grant store — MOCKED (D2):** each Hospital Node seeds an in-memory grant store from the fictional `demo-data/access.json` at startup (HC-115). Grants recorded or revoked through the access grants API change only that process's copy: they are lost on restart, never written back, and never reach another node. Callers are not authenticated. Tests, and Hospital A and B running side by side, checked that a grant recorded on Hospital B allowed Dr. Ines's query there, was refused on Hospital A, and was refused on Hospital B after revocation. This is not consent management or production security.
- **Federated patient aggregation — MOCKED (D2), opt-in:** with `FEDERATION_NODES=simulated`, [`services/federation/`](../services/federation/README.md) serves `POST /v1/federated-queries` on port 8300 and asks the nodes in its node registry. Its Hospital Nodes are simulated in process from `demo-data/`. Each simulated node reads only its own organization's records, answers in the Hospital Node contract format, and checks the fictional grant or synchronization decision itself, denying by default. The service merges the answers into a transient timeline with one status per node. The demo request for Patient A returns a `partial` result because the private practice's DMI is disconnected. Tests check responses against the contract. This is not node-to-node exchange, real authorization, or production security.
- **Governance hospital approval, synchronization, and research decisions — MOCKED (D1):** a decision recorded in the Governance Portal (HC-073, HC-076, HC-078) is built in the browser and kept in local, in-memory portal state with a `decision_recorded` audit event, both labelled simulated. Nothing is sent to a Governance Node (the decision APIs, HC-131 to HC-133, are PLANNED), the Research Service, or a Hospital Node, persisted, or anchored to a ledger, so a simulated approval authorizes no real exchange or execution; a reload or the portal's reset returns to the canonical fixtures. The reviewer identity is the fictional demo reviewer, not an authenticated user.

No other product mock exists. Planning documents permit further fictional fixtures and deterministic demo behavior, but those plans are not implementation.
