Status is based on repository inspection, not product intent. Use the [shared vocabulary](README.md#status-vocabulary). Re-check code, tests, tickets, and ADRs before relying on this snapshot.

- **Repository structure — IMPLEMENTED:** named boundaries exist for apps, instances, services, integrations, contracts, infrastructure, production, IoT, documentation, scripts, and cross-system tests.
- **Documentation — IMPLEMENTED:** canonical product vision, architecture, component boundaries, planning, contribution rules, and status guidance exist.
- **Planning documents — IMPLEMENTED:** backlog, milestones, canonical demo, and dependency diagrams exist as plans only.
- **GitHub governance — IMPLEMENTED:** issue/PR templates, CODEOWNERS placeholder, Dependabot placeholder, and workflow files exist.
- **Workflow behavior — IMPLEMENTED but limited:** project automation exists; CI, lint, tests, and Docker workflows are manual placeholders rather than product validation pipelines.
- **PlatformIO preparation — IMPLEMENTED placeholder:** `platformio.ini` and empty firmware directories exist.
- **Web design system — IMPLEMENTED (D1):** `design-system/` contains Tailwind CSS v4 tokens, base typography, presentational React components (buttons, form fields, cards, tables, badges, alerts, navigation/shell, loading/empty/error states, timeline), explicit demo labelling, and a showcase page ([ADR-0002](decisions/ADR-0002-web-design-system.md)). Build, lint, showcase rendering, and consumption by a throwaway portal outside the repository were checked; no portal in the repository uses it yet, and no automated component tests exist. Mobile reuse is OPEN.
- **Deployment/production preparation — IMPLEMENTED documentation/placeholders:** no deployed runtime or selected provider is implied.

- **AI Services runtime skeleton — VALIDATED (local):** [`services/ai/`](../services/ai/README.md) is a FastAPI service with `GET /health`, framework-free Domain/Application layers, and pytest tests (use case, HTTP, layer boundaries). Its tests, ruff checks, and local `fastapi dev`/`fastapi run` servers were verified. It exposes no real AI capability and is not deployed.
- **Hospital Node runtime skeleton — IMPLEMENTED:** [`instances/hospital-node/`](../instances/hospital-node/README.md) is a FastAPI app with pinned dependencies and pytest tests (use case, HTTP, layer boundaries). One codebase runs one process per hospital: each instance loads its hospital identity (node and organization ids), port, and local storage location from the JSON file named by `HOSPITAL_NODE_CONFIG`, and refuses to start without a valid one (HC-112, D2). Fictional demo configurations exist for Hospital A, Hospital B, and the private practice. Its only endpoint is `GET /health` (HC-111, D2): a liveness check reporting the configured identity, no capabilities, the clinical repository's record counts, and a notice that the repository is MOCKED and no clinical API is served. Tests, ruff, and Hospital A and B running side by side on ports 8101 and 8102 were checked. Nothing uses its storage location yet, and it is not deployed.
- **AI provider port — IMPLEMENTED, provider MOCKED:** the provider-neutral `AiProvider` port (HC-151) lives in `services/ai/application/`. Its only adapter is a deterministic mock, reported at `GET /ai-provider`. Outputs carry provenance and stay pending human review. No real model is called.
- **Governance Portal shell, dashboard & pending hospital approval list (HC-070, HC-071, HC-072) — IMPLEMENTED (D1):** [`apps/web/governance-portal/`](../apps/web/governance-portal/README.md) is a React 19 + TypeScript + Vite SPA configured per [ADR-0001](decisions/ADR-0001-web-frontend-technology.md) and [ADR-0002](decisions/ADR-0002-web-design-system.md). It consumes `@hackcure/design-system` and canonical fictional demo fixtures (`demo-data/governance.json`, `organizations.json`, `people.json`, `notifications.json`). It implements a complete governance dashboard with reviewer alerts (Pr Olfa Hamdi), federated hospital nodes health monitoring, executive KPI metrics, pending hospital approval list queue with search/filter/document-completeness indicators, prioritized action queues, decision records, cryptographic SHA-256 ledger proof verification, and resilient loading/empty/error states. Vitest suite passes. Fixed dev port is 5174.

## Not implemented

- **Web products — mostly PLANNED:** Hospital Portal and Research Portal contain documentation only. Governance Portal shell is IMPLEMENTED at D1 (see Implemented).
- **Mobile products — PLANNED:** Patient App and Clinician App contain documentation only. Flutter + Dart and the Android development path are CONFIRMED by [ADR-0004](decisions/ADR-0004-mobile-technology.md); no dependencies, application code, or generated platform project exists.
- **Backend runtime strategy — CONFIRMED:** [ADR-0003](decisions/ADR-0003-backend-runtime-strategy.md) selects Python + FastAPI for every Node and service. Only the AI Services and Hospital Node skeletons exist so far (see Implemented); no other runtime has been created.
- **Hospital Node — PLANNED beyond its skeleton and mock repository:** no local clinical API, persistent storage, authenticated node identity, consent, audit, or Federation implementation; per-hospital configuration is demo-only and unauthenticated; its health endpoint is liveness only.
- **Governance Node — PLANNED:** no runtime, policy engine, authorization, audit persistence, or ledger adapter.
- **DMI Adapter — PLANNED:** its Hospital Node-local boundary exists, but no port, mapping, configuration, fixture, or implementation.
- **Federation Service — partially IMPLEMENTED:** the runtime serves the federated patient query. By default it asks each registered Hospital Node over real HTTP (HC-145), parses answers strictly, and marks a result `mocked` when a node says it answered from fixtures. No Hospital Node serves the endpoint yet, so live queries report every node `unavailable`; the successful path is covered by tests only. `FEDERATION_NODES=simulated` switches to the HC-141 MOCKED nodes (see Mocked behavior). In `http` mode, failures are handled (HC-147): connection errors, `503`, and timeouts are retried once with the same `query_id` within a 5-second budget, and a node that failed 3 consecutive queries is paused for 30 seconds and reported `not_asked` with `circuit_open` (in memory). Also in `http` mode, a node whose latest capability check shows it cannot answer is not asked and is reported `not_asked` with the reason (HC-146); nodes never checked or unreachable are still asked. The service also serves a node registry (HC-142): register, update, list, get, and remove nodes. Federated queries ask only registered nodes. The registry is kept in memory, its write operations are unauthenticated, and the Governance approval reference on each registration is not verified. Capability discovery (HC-143) calls each registered node's `GET /v1/federation/node` over real HTTP on request and keeps the latest result in memory. No Hospital Node serves that endpoint yet, so live checks report `no_federation_interface` or `unreachable`; the successful path is covered by tests only. Temporary sync authorization (HC-144): before any node is asked under a synchronization decision, the service checks it with the Governance Node over real HTTP and asks only the organizations Governance authorizes. No Governance Node exists yet, so live sync-basis queries return `503` and ask no node; the authorized path is covered by tests only. Persistent registry storage, node identity and service authentication, Governance verification of patient access grants, the Hospital Node side of the Federation interface, synchronization, and audit are PLANNED.

- **Research Service and Compute-to-Data — PLANNED:** no orchestrator, sandbox, Hospital Node agent, execution, or controlled-output validation.

- **Communication contracts — mostly PLANNED:** three API contracts are defined: AI clinical extraction, [`clinical-extraction.v1.yaml`](../contracts/api/ai/clinical-extraction.v1.yaml) (HC-152); medication safety check, [`medication-safety-check.v1.yaml`](../contracts/api/medication-safety/medication-safety-check.v1.yaml) (HC-160); and SciAgents scientific investigation, [`scientific-investigation.v1.yaml`](../contracts/api/sciagents/scientific-investigation.v1.yaml) (HC-170). The Federation Service implements `federated-patient-query.v1.yaml` with MOCKED nodes (HC-141) and implements `node-registry.v1.yaml` (HC-142). ## Mocked behavior

- **Canonical demo data — MOCKED (D1):** `demo-data/` holds fictional JSON for three hospitals, a private practice, the Governance / Ethics Authority, three patients, clinicians, encounters, medications, labs, access grants, synchronization and research requests, decisions, audit events, simulated ledger proofs, research jobs, a SciAgents fixture, alerts, and notifications ([ADR-0005](decisions/ADR-0005-canonical-demo-data.md)). `python demo-data/check_fixtures.py` passes. Medicines and the interaction rule are invented and not validated. The Federation Service's simulated nodes read it (HC-141).
- **AI clinical extraction — MOCKED (D1):** `POST /v1/clinical-extractions` in [`services/ai/`](../services/ai/README.md) implements the HC-152 contract with a deterministic fixture extractor. It recognises one fictional demo transcript (Patient A) and returns a fixed draft; any other text returns an empty draft. Every response is labelled `provenance.mocked: true` and `review_status: pending_clinician_review`. Its responses are checked against the contract by automated tests. This is not clinical intelligence.
- **AI provider — MOCKED (D1):** `DeterministicMockAiProvider` (HC-151) returns fixed `[MOCK]` templates and never echoes input. It is not AI and not validated intelligence.
- **Hospital Node clinical repository — MOCKED (D2):** each [`instances/hospital-node/`](../instances/hospital-node/README.md) instance loads, at startup and read-only into memory, the fictional `demo-data/records/` file named by its configuration (HC-113). It refuses to start if the file is not marked fictional, is held by another organization, or holds a malformed record. A `ClinicalRepository` port returns one patient's records held by that node; no API exposes them yet (HC-114). Tests and Hospital A and B running side by side were checked, as was a refused start with another hospital's file. This is not real storage, a DMI integration, or a FHIR model; persistence and FHIR mapping are OPEN.
- **Federated patient aggregation — MOCKED (D2), opt-in:** with `FEDERATION_NODES=simulated`, [`services/federation/`](../services/federation/README.md) serves `POST /v1/federated-queries` on port 8300 and asks the nodes in its node registry. Its Hospital Nodes are simulated in process from `demo-data/`. Each simulated node reads only its own organization's records, answers in the Hospital Node contract format, and checks the fictional grant or synchronization decision itself, denying by default. The service merges the answers into a transient timeline with one status per node. The demo request for Patient A returns a `partial` result because the private practice's DMI is disconnected. Tests check responses against the contract. This is not node-to-node exchange, real authorization, or production security.

No other product mock exists. Planning documents permit further fictional fixtures and deterministic demo behavior, but those plans are not implementation.
