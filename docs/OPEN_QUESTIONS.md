# Open Questions

These questions are OPEN. Do not answer them through implementation without the required evidence and ADR.

- How will the Flutter mobile apps reuse or translate the web design-system tokens without depending on the React package ([ADR-0002](decisions/ADR-0002-web-design-system.md), [ADR-0004](decisions/ADR-0004-mobile-technology.md))?
- How will one Hospital Node codebase load per-hospital configuration (identity, port, storage) for several demo hospitals? (The runtime itself is decided by [ADR-0003](decisions/ADR-0003-backend-runtime-strategy.md).)
- What canonical clinical model, FHIR version, profiles, terminology, and validation strategy are required?
- Which persistence technologies and data models fit each bounded context?
- Which authentication provider and identity architecture will serve patients, clinicians, researchers, organizations, and Nodes?
- How will consent, legal authority, revocation, retention, restriction, and erasure differ by jurisdiction?
- How does one patient's access grant reach every Hospital Node holding their records? In the [access grants contract](../contracts/api/patient-access/patient-access-grants.v1.yaml) v1 (HC-115), each node records and enforces its own grants, so a grant recorded on one node is unknown to the others. Since HC-136 the Governance Node evaluates a synchronization's grant with the target organization's node over HTTP and keeps no copy; how it discovers those nodes in production (a demo directory file today), how the two authenticate each other, and whether Governance should keep a consent record are undecided. Who may call the grants API (patient, delegate, Patient App identity) is also undecided.
- Which transport and protocol will carry Federation queries, synchronization, and node discovery?
- How will node identity, signing, authorization tokens, key rotation, and trust establishment work?
- How does a Hospital Node verify a synchronization authorization itself, and should Governance issue signed, time-limited tokens instead of answering online checks? HC-144 implements only the Federation Service's online check ([`sync-authorization-check.v1.yaml`](../contracts/federation/sync-authorization-check.v1.yaml)), without service authentication.
- Who may register, update, or remove entries in the Federation [node registry](../contracts/federation/node-registry.v1.yaml), and where are registrations persisted? In v1 the writes are unauthenticated and the registry is in memory; the Governance approval each registration cites is not verified.
- How is one patient matched across organizations? The [Federation contracts](../contracts/federation/README.md) carry an ecosystem-level `patient_ref` that each Hospital Node maps to its local identifier; the matching and enrolment process is undecided.
- Who may read a Hospital Node's audit trail ([`hospital-audit-events.v1.yaml`](../contracts/api/hospital-audit/hospital-audit-events.v1.yaml)), how those readers are authenticated, and how long events are retained? In v1 events are kept in memory and readers are not authenticated (HC-116).
- Who writes and approves a new version of the governance policy ([`governance-policies.v1.yaml`](../contracts/api/governance/governance-policies.v1.yaml), HC-135), through which interface, and which rules it should cover beyond the review limits it holds today (purposes, variables, organizations)? In v1 versions are fictional data read at startup.
- The same questions for the Governance Node's own audit trail ([`governance-audit-events.v1.yaml`](../contracts/api/governance/governance-audit-events.v1.yaml), HC-134), plus how a durable trail is kept consistent with the decisions it records (in v1 a decision is stored, then audited, in two in-memory stores).
- Is an Immutable Audit Ledger required? It stays OPTIONAL. [ADR-0007](decisions/ADR-0007-permissioned-audit-ledger.md) accepts Hyperledger Besu (QBFT) under trust model B, following the [HC-193 evaluation](research/2026-10-11-permissioned-ledger-evaluation.md): independent organizations run validators. Which organizations (Hospital Nodes, a regulator), how they join, and on what terms is undecided. Until then the only chain is a local single-validator one, which gives no assurance independent of the Governance Node. Also open: whether co-operators may read each decision's outcome, time, and organizations, which the ledger keeps permanently.
- Which AI hosting mode, evaluation criteria, and clinical review controls are acceptable? (Providers for development and demos are decided by [ADR-0006](decisions/ADR-0006-ai-provider-strategy.md); a hosted deployment needs a Claude adapter that does not depend on an interactive Claude Code login.)
- Which components may call the AI clinical extraction API with clinical source text, and is AI Services hosted inside the hospital boundary or as a company service? This decides whether clinical text leaves the Hospital Node. ([HC-152 contract](../contracts/api/ai/clinical-extraction.v1.yaml).)
- Should extracted measurement units be coded in UCUM and items mapped to a terminology (for example SNOMED CT) before clinician review, or only after?
- Which validated medication-interaction and clinical terminology sources will be used?
- How is the medication interaction rule set distributed to every Hospital Node and kept at one version? [ADR-0008](decisions/ADR-0008-medication-safety-check-host.md) places the [medication safety check](../contracts/api/medication-safety/medication-safety-check.v1.yaml) on each Hospital Node; today each reads the same fictional file at startup.
- Which medication terminology (for example RxNorm or ATC) identifies medications across organizations, so interactions can be matched reliably?
- Which research execution sandbox, package policy, isolation controls, and output-disclosure process are required?
- SciAgents' inspected API exposes open `/hypotheses` HTTP endpoints and SSE progress, accepts exactly two keywords, and reports no calibrated confidence. Hosting, rate limits, service authentication, and the supported biomedical vocabulary remain OPEN. The [HC-170 contract](../contracts/api/sciagents/scientific-investigation.v1.yaml) is repository-side; HC-171 must normalize the observed inline/queued behavior and must not expose the open upstream API to browsers.
- Would a future decision to send controlled-result summaries to the external SciAgents system require its own Governance authorization or data-processing agreement beyond the research project's approval? HC-170 v1.1 currently forbids that content and sends only two non-identifying concept labels upstream.
- Which notification providers and delivery protocols will be used?
- Which container runtime, deployment providers, hosting topology, observability stack, and disaster-recovery approach are appropriate?
- Which actual DMI/HIS systems, interfaces, schemas, mappings, and local installation constraints apply to each participating hospital?
- Is IoT required; if so, which hardware, embedded framework, protocol, and security constraints apply?
- Which business-model assumptions from the product vision are validated for the hackathon and for later operation?
